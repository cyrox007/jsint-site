# Публичный API и внешние frontend-витрины

## Цель

`jsint-site` является единым backend и центром управления контентом. Публичная часть, встроенная в сам проект, и отдельные frontend-проекты используют одну централизованную базу публикаций и не должны создавать собственные backend-сервисы.

Каждая тематика или самостоятельная публичная витрина представлена сущностью `Site`. Контент разделяется по `site_id`, а одна публикация при необходимости может размещаться на нескольких сайтах через `publication_sites`.

## Базовый контракт

Публичный API имеет версию `v1`:

```text
/api/public/v1/sites/<site_key>
```

Основные маршруты:

```text
GET /api/public/v1/sites/<site_key>
GET /api/public/v1/sites/<site_key>/bootstrap
GET /api/public/v1/sites/<site_key>/categories
GET /api/public/v1/sites/<site_key>/publications
GET /api/public/v1/sites/<site_key>/publications/<slug>
GET /api/public/v1/sites/<site_key>/pages/<slug>
GET /api/public/v1/sites/<site_key>/media
```

`bootstrap` предназначен для первого запуска внешней витрины. Он возвращает публичную идентичность сайта, рубрики и последние публикации одним запросом. Он не является контрактом дизайна или SEO.

Ответы содержат заголовок:

```text
X-JSInt-Public-API: jsint-public-v1
```

## Разделение данных

- `Site` задаёт идентификатор контентного канала, название, домен и разрешённые origin. Внутренние настройки встроенной витрины могут храниться рядом, но внешний frontend не обязан и не должен использовать их как контракт дизайна или SEO.
- Рубрики принадлежат конкретному сайту.
- Публикация имеет основной сайт-владелец.
- Дополнительные размещения публикации управляются через `publication_sites`.
- Публичный API всегда выбирает данные по `site_key` и не должен отдавать материалы соседней витрины.
- Администратор переключает рабочий сайт в общей админке и управляет всеми витринами из одного интерфейса.

Отдельная база данных для каждого frontend не требуется.

## Структурированные данные публикаций

Общие поля публикации остаются одинаковыми для всех витрин: название, текст, рубрика, тип, даты и статус публикации. Если конкретному сайту нужны дополнительные данные, они передаются отдельным версионированным профилем:

```json
{
  "data": {
    "schema": "logos.article",
    "version": 1,
    "data": {
      "abstract": "Аннотация",
      "keywords": ["философия", "онтология"],
      "bibliography": ["Источник 1", "Источник 2"]
    }
  }
}
```

Внутреннее `extra_data` не является публичным контрактом и наружу целиком не отдаётся. Это важно, чтобы служебные поля встроенного JSInt, в том числе его SEO-настройки, не становились зависимостью внешнего frontend.

Профили хранятся раздельно по ключу сайта. Поэтому одна и та же публикация может быть основной для JSInt и одновременно иметь `logos.article@1` только для размещения Logos. Публичный API выбирает профиль по запрошенному `site_key`.

Схема и версия позволяют развивать структуру конкретной витрины независимо от общей таблицы публикаций. Для JSInt дополнительные поля не появляются, пока они ему не нужны.

## CORS

Внешний frontend должен быть явно разрешён в настройках соответствующего сайта:

```text
Админка → Сайты → Настройки сайта → Разрешённые origin публичного API
```

Указываются только origin без пути, например:

```text
https://logos.example.org
http://localhost:8080
```

Публичный frontend не должен хранить API-ключи, секреты, токены подписи или административные учётные данные. Для чтения опубликованного контента используется только публичный GET API.

## Контракт для logos-frontend

`logos-frontend` должен знать только:

```text
VUE_APP_SERVER=https://jsinteractive.ru
VUE_APP_SITE_KEY=logos
```

Frontend:

1. загружает `/bootstrap`;
2. строит навигацию и список рубрик из ответа;
3. получает списки публикаций с фильтром `category`;
4. получает отдельную публикацию по `slug`;
5. не содержит маршрутов создания/редактирования публикаций и собственной авторизации для CMS;
6. самостоятельно формирует `title`, `meta description`, canonical, OpenGraph, структурированные данные и другие SEO-представления из полученных фактов о публикации.

Создание, редактирование, публикация, media и размещение по витринам выполняются в админке `jsint-site`. Дизайн публичной части и SEO конкретного внешнего frontend принадлежат самому frontend.

## Правило развития

Новые frontend-проекты подключаются как новые `Site`, а не как новые backend-приложения. Если новому frontend не хватает данных, сначала расширяется версионированный публичный API, затем меняется клиент. Нельзя добавлять прямой доступ frontend к PostgreSQL, Redis, внутренним административным маршрутам или операторскому control plane.


## Граница ответственности

```text
jsint-site
  ├─ хранит публикации, рубрики, страницы и media
  ├─ определяет, к какому Site относится материал
  ├─ управляет публикацией и размещением по витринам
  └─ отдаёт версионированный публичный API

jsint-site встроенный frontend
  ├─ собственный дизайн
  └─ собственное SEO

logos-frontend
  ├─ собственный дизайн
  ├─ собственная маршрутизация
  └─ собственное SEO
```

Таким образом, один и тот же backend может обслуживать несколько внешне и семантически разных публичных сайтов, не превращая их в темы одного общего frontend.
