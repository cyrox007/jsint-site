# Единая система публикаций, лицензий и релизов

`jsint-site` объединяет публичный сайт, CMS и операторский control plane Workspace Organizer.

## URL

- публичный сайт: `https://jsinteractive.ru/`;
- админка: `https://jsinteractive.ru/<ADMIN_ROUTE_PREFIX>/`;
- machine API: `https://jsinteractive.ru/api/notes/v1/`;
- локальный signer оператора: `http://127.0.0.1:17843/v1`.

## Криптографическая граница

Приватные ключи лицензий и обновлений **не должны находиться на web-сервере**.

Обычный операторский сценарий для обоих типов ключей работает в браузере:

- для лицензий оператор выбирает существующий файл `.license-secret`;
- для релизов оператор выбирает существующий файл `.update-secret`;
- браузер проверяет ключ по публичному trust root из `config/notes_trust.py`;
- приватный ключ импортируется как неэкспортируемый `CryptoKey`;
- после успешной проверки ключ может храниться только в локальном IndexedDB текущего браузерного профиля;
- исходное содержимое файла ключа не отправляется на сервер и не сохраняется в PostgreSQL;
- подпись выполняется через Web Crypto;
- сервер получает только уже подписанный `wo1...` или `wou1...` результат и повторно проверяет подпись.

Web-сервер знает только публичные trust roots. Пути к приватным ключам и содержимое файлов ключей в production-конфигурации отсутствуют.

## Выпуск лицензии через браузер

Админка → «Лицензии → Выпустить».

Оператор задаёт параметры лицензии, затем один раз выбирает файл `.license-secret`.
Браузер проверяет его по production trust root и сохраняет неэкспортируемый ключ локально, если IndexedDB доступен.

Формат файла:

```text
wo-ed25519-secret-v1:<base64url 64-byte Ed25519 secret>
```

При выпуске:

1. браузер формирует строго структурированные данные лицензии;
2. приватный ключ используется только локально для Ed25519-подписи;
3. в web-приложение отправляется только готовый `wo1...` token;
4. сервер повторно проверяет подпись и параметры;
5. лицензия записывается в реестр;
6. для совместимости со старыми клиентами может быть показан одноразовый activation code.

### Локальный signer

В репозитории остаётся отдельный loopback signer на `127.0.0.1:17843` как совместимый/аварийный инструмент и для офлайн-сценариев. Обычный web-интерфейс выпуска лицензий и релизов от него не зависит.

Signer не является обязательным компонентом production VPS и не должен хранить ключи на сервере. Если он используется вручную, его следует запускать только на доверенном компьютере оператора и останавливать после операции.

## Реестр лицензий

В PostgreSQL хранятся:

- `installation_id`;
- `license_id`;
- уже подписанный `wo1...` token;
- `customer`, `edition`, `max_users`, `features`;
- срок действия лицензии;
- ограничения доступа к обновлениям: `updates_until`, `max_version`;
- SHA-256 одноразового activation code или download credential;
- состояние последней связи клиента.

Private key и локальный путь к нему в БД отсутствуют.

## Параметры лицензии

При обычном выпуске оператор указывает:

- Installation ID;
- владельца лицензии;
- License ID;
- edition;
- лимит пользователей;
- features;
- дату начала;
- срок лицензии.

Доступ к обновлениям для обычного выпуска автоматически действует до даты окончания лицензии. Ограничение по `version_code` в этом сценарии не задаётся.

Результат состоит из двух разных сущностей:

- `wo1...` — лицензия Workspace Organizer;
- activation code — одноразовый код совместимости для старых установок; Workspace Organizer 1.0.2+ может активировать online updater непосредственно по лицензии.

### Импорт готовой лицензии

Вкладка «Импорт готовой» остаётся для полностью офлайн-процесса. Можно
подписать лицензию штатным tooling Workspace Organizer на отдельной машине и
вставить уже готовый `wo1...`.

## Presence / last seen

Control plane не пытается входящим соединением «пинговать» клиентскую
установку: за NAT или в закрытой сети это ненадёжно.

Статус строится по последнему исходящему запросу клиента:

- «На связи» — контакт не старше 15 минут;
- «Недавно» — контакт за последние 24 часа;
- «Нет связи» — контакта не было более суток;
- «Нет данных» — клиент ещё не связывался с control plane.

Last seen обновляется при:

- activation;
- heartbeat;
- запросе feed;
- manifest;
- signature;
- ZIP.

Machine endpoint:

```text
POST /api/notes/v1/heartbeat
```

Он использует те же update credentials:

```text
Authorization: Bearer <64hex credential>
X-Notes-Installation: <installation UUID>
```

«Нет связи» не означает, что offline/закрытая установка неисправна.

## Выбор обновления для конкретной версии клиента

Новые версии Workspace Organizer передают при обращении к update API только
несекретные сведения о фактически установленной версии:

```text
X-Notes-Version: 1.0.5
X-Notes-Version-Code: 10005
```

Эти заголовки не являются полномочиями: доступ по-прежнему определяется
действующей лицензией, download credential, `updates_until` и `max_version`.
Клиентский `version_code` используется только для выбора подходящего
подписанного релиза.

Для `feed.json` сервер выбирает самый новый активный релиз, у которого
`min_source_version_code` допускает прямое обновление с версии клиента.
Поэтому установка, пропустившая несколько публикаций, получает не
несовместимый «самый новый вообще» релиз, а ближайший подходящий шаг цепочки.
После успешного обновления следующий запрос уже сообщает новый `version_code`
и получает следующий совместимый релиз.

Старые опубликованные клиенты, которые ещё не передают эти заголовки,
обслуживаются по прежнему правилу до завершения переходного окна. Постоянный
одношаговый контракт начинается с клиентской базы 1.0.5.

## Релизы

### Реестр

Показывает:

- version;
- version_code;
- channel;
- source commit;
- минимальный source version_code;
- PHP requirement;
- signing key;
- ZIP;
- SHA-256;
- время публикации;
- active/inactive.

Релиз можно снять с feed без удаления записи.

### Обычный выпуск из GitHub

В обычной работе оператор использует одну форму во вкладке «Релизы → Выпустить».

При первом использовании нужно выбрать существующий файл update key.
После проверки браузер сохраняет неэкспортируемый `CryptoKey` локально,
поэтому в следующих выпусках обычно достаточно нажать «Выпустить релиз».
Система всегда берёт последний опубликованный GitHub Release.

Дальше система сама:

1. получает официальный ZIP из настроенного `NOTES_RELEASE_GITHUB_REPOSITORY`;
2. проверяет SHA-256, Git tag, commit и версию внутри ZIP;
3. при наличии `.sha256` и `.source-sha` дополнительно сверяет их, но эти файлы не обязательны;
4. вычисляет стандартный минимальный `version_code` предыдущей версии;
5. строит точный manifest на сервере;
6. передаёт manifest в браузер;
7. браузер использует проверенный локальный `CryptoKey` и подписывает manifest через Web Crypto;
8. на сервер отправляются только manifest и готовая подпись `wou1...`; manifest передаётся JSON-запросом без HTML-form нормализации переводов строк, чтобы сервер проверял ровно те байты, которые были подписаны;
9. сервер повторно проверяет подпись и соответствие уже скачанного ZIP, после чего публикует релиз в ленту.

Приватный update key не отправляется на web-сервер и не сохраняется сайтом.
Генерировать новый ключ для каждого релиза не требуется.

Для текущего публичного `cyrox007/Notes` значение
`NOTES_RELEASE_GITHUB_TOKEN` не требуется. Если репозиторий станет приватным,
серверу один раз задаётся отдельный GitHub token только с правом чтения релизов.

### Аварийный режим

Старые серверные маршруты ручной загрузки ZIP и импорта готового manifest/signature
сохранены для совместимости и восстановления. В обычном интерфейсе они скрыты,
чтобы не усложнять выпуск релиза.

## Release storage

ZIP хранится вне application tree:

```text
/var/lib/jsint-site/notes-releases
```

Пример:

```bash
sudo install -o root -g jsint-site -m 0640 \
  ./workspace-organizer-v1.0.2.zip \
  /var/lib/jsint-site/notes-releases/workspace-organizer-v1.0.2.zip
```

## Активация online updater

На клиенте:

```bash
php bin/update_activate.php \
  --server=https://jsinteractive.ru/api/notes/v1/ \
  --installation-id=<UUID> \
  --activation-file=/private/activation-code \
  --credentials-out=/private/update-access.json
```

После активации:

```env
UPDATE_ACCESS_MODE=online
UPDATE_CREDENTIALS_FILE=/private/update-access.json
UPDATE_FEED_URL=https://jsinteractive.ru/api/notes/v1/stable/feed.json
```

## Операторский аудит

В административной панели доступен append-only журнал control plane.

Журнал сохраняет:

- UUID и email оператора на момент действия;
- тип действия;
- целевую лицензию, installation или release;
- результат операции;
- безопасные технические детали: channel, version, source SHA, package SHA-256.

В журнал не попадают:

- `wo1...` и `wou1...` токены;
- activation codes;
- download credentials;
- приватные ключи;
- содержимое файлов ключей.

Таблица защищена PostgreSQL trigger: обычные `UPDATE` и `DELETE` запрещены. Минимальный срок хранения задаётся `OPERATOR_AUDIT_RETENTION_DAYS`; приложение само старые записи не удаляет. Если в будущем потребуется архивирование, оно должно выполняться отдельной административной процедурой с экспортом и контролируемым удалением вне web-интерфейса.

Machine API добавляет в этот журнал только ошибки выдачи update artifacts. Это позволяет видеть revoked/expired попытки без хранения credentials.

## Мониторинг control plane

Главный dashboard показывает технические показатели:

- installations на связи за последние 15 минут;
- лицензии с `updates_until` в ближайшие 30 дней;
- последние зарегистрированные релизы;
- количество ошибок update API за 24 часа;
- количество отказов по revoked/expired entitlement;
- PostgreSQL, Redis и Celery heartbeat.

Содержимое пользовательских данных Workspace Organizer в мониторинг не передаётся.

## Предрелизная проверка

Перед подписью manifest обычный GitHub-выпуск выполняет preflight:

1. сверяет Git tag, версию в ZIP и GitHub prerelease-state;
2. проверяет source SHA и package SHA-256;
3. сравнивает новый `version_code` с текущей активной головой канала;
4. останавливает выпуск, если версия не выше текущей головы;
5. отдельно предупреждает о prerelease-подобном имени версии в канале stable.

Вверху раздела «Релизы» отображается read-only состояние каналов stable/beta/alpha: текущая версия, `version_code`, manifest и signature. Релиз можно временно снять с feed и вернуть обратно без удаления записи.

## Production environment

```env
NOTES_CONTROL_PLANE_ENABLED=true
NOTES_UPDATE_API_PREFIX=/api/notes/v1
NOTES_UPDATE_BASE_URL=https://jsinteractive.ru/api/notes/v1/
NOTES_RELEASE_STORAGE_PATH=/var/lib/jsint-site/notes-releases
NOTES_RELEASE_GITHUB_REPOSITORY=cyrox007/Notes
NOTES_RELEASE_GITHUB_TOKEN=
NOTES_RELEASE_DEFAULT_REQUIRES_PHP=8.1.0

# Для public repository token не нужен. Для private repository используется
# отдельный read-only token; его нельзя помещать в Git, release ZIP или логи.

# Совместимый loopback signer для аварийных/ручных сценариев.
# Обычный выпуск лицензий и релизов выполняется Web Crypto в браузере.
NOTES_OPERATOR_SIGNER_URL=http://127.0.0.1:17843/v1
```

Пути к приватным ключам в production env отсутствуют. Для обычного выпуска
лицензии и релиза приватный ключ выбирается локально в браузере и не отправляется
на сервер. Loopback signer остаётся только совместимым/аварийным инструментом и
не участвует в штатном web-сценарии.

## Healthcheck

- общий: `GET /healthz`;
- control plane: `GET /api/notes/v1/health`.

Healthcheck web-сервера не зависит от локальных signing-инструментов оператора.
